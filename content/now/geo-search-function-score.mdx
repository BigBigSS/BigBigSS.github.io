做酒店搜索时，"附近搜索"和"按城市搜索"看起来像同一个需求，底层却是两套召回逻辑。

按城市搜，本质是按行政区域过滤：给定一个城市，把挂在这个城市下的酒店捞出来。但 POI、机场、车站这类**点类型**没有行政边界——用户搜"某地铁站附近的酒店"，期待的是以这个点为圆心、按距离铺开的结果。这种场景只能走 geo 半径搜索：给一个中心坐标和半径，召回圆内的酒店，再排序。

召回不难。难的是排序，而排序恰好是这次性能问题的来源。

## 排序不只是按距离

如果"附近"只按距离升序排，那很简单，ES 的 `geo_distance` 排序原生就支持。但真实业务里，距离只是其中一维。一个合理的"附近"排序，至少要同时揉进几个因素：

- **距离**：越近越靠前，但要平滑衰减，而不是硬切；
- **酒店评分**：同样距离下，分高的优先；
- **服务/口碑分**：另一个质量维度；
- **搜索热度**：被搜得多、被点得多的，适当加权。

也就是说，最终排序分是这几个因素的加权组合。最直觉的实现，就是写一段脚本，把这些字段读出来，按自己的公式算一个总分：

```groovy
// script_score：每个命中文档都要跑一遍这段脚本
double distanceKm = doc['location'].arcDistance(params.lat, params.lon) / 1000;
double distanceFactor = 1.0 / (1.0 + distanceKm);   // 距离越远，因子越小
double base = doc['hotel_score'].value * params.wHotel
            + doc['service_score'].value * params.wService
            + doc['search_heat'].value * params.wHeat;
return base * distanceFactor;
```

逻辑上没问题，结果也对。问题是它慢。

## 为什么 script_score 会成为瓶颈

`script_score` 的代价，藏在"每个命中文档都要跑一遍脚本"这句话里。

半径搜索在热门区域很容易命中几千上万家酒店。每一个命中文档，ES 都要：把脚本编译后的字节码拿出来执行一次、从 doc values 里读出好几个字段、算一遍 `arcDistance`、做几次浮点乘加。脚本本身是通用执行引擎，拿不到任何原生算子的优化——它对 ES 来说是个黑盒，只能老老实实逐个文档解释执行。

命中越多，这部分纯打分的开销就越线性地往上堆。在我们的线上等价查询里，某个 2km 半径、命中量较大的热门区域场景，整个接口稳定在 **200ms 左右**，火焰图上大头就是脚本评分阶段。召回其实很快，慢的全是打分。

这里值得记住的边界：**`script_score` 适合"少量文档 + 复杂打分"**。如果你的查询前置过滤已经把候选集压到几十上百个，脚本那点开销无所谓，灵活性反而是优势。但一旦候选集是几千上万，逐文档跑脚本就成了性能黑洞——这正是地理半径搜索的典型形态。

## 换成 function_score

ES 其实为"多因素加权排序"准备了原生算子：`function_score`。它把每个排序因素表达成一个内置 function，由引擎用编译好的原生实现去算，而不是解释执行脚本。

把上面那段脚本翻译过来，大致是这样：

```json
{
  "function_score": {
    "query": { "geo_distance": { "distance": "2km", "location": { "lat": 30.58, "lon": 114.30 } } },
    "functions": [
      {
        "gauss": {
          "location": { "origin": { "lat": 30.58, "lon": 114.30 }, "scale": "1km", "decay": 0.5 }
        }
      },
      { "field_value_factor": { "field": "hotel_score",  "factor": 1.0, "modifier": "none" } },
      { "field_value_factor": { "field": "service_score", "factor": 0.8, "modifier": "none" } },
      { "field_value_factor": { "field": "search_heat",  "factor": 0.5, "modifier": "log1p" } }
    ],
    "score_mode": "sum",
    "boost_mode": "replace"
  }
}
```

每个排序维度都有了原生对应：

- 距离衰减用 **`gauss` 衰减函数**表达。`scale` 和 `decay` 控制衰减曲线，比手写的 `1/(1+d)` 更可控，也更符合"近处差异敏感、远处趋于平缓"的直觉；
- 酒店分、服务分用 **`field_value_factor`** 直接读字段值参与打分；
- 搜索热度同样用 `field_value_factor`，套一个 `log1p` 把长尾热度压平，避免极热的点把别的维度完全淹没；
- **`score_mode`** 决定这几个 function 之间怎么合并（这里求和），**`boost_mode`** 决定最终分是否还要乘上原查询的相关性分。

关键差别在于：这些 function 是 ES 编译进引擎的原生算子，逐文档执行时没有脚本解释开销，字段读取和打分都走优化过的路径。同样的命中量，引擎能批量、低成本地算完。

落到那个 2km 热门区域场景，等价查询从约 **200ms 降到约 70ms**——延迟砍掉三分之二，而距离、酒店分、服务分、热度这几个排序维度一个没丢。

## 这次的取舍

复盘下来，真正的决策点不是"哪个 API 更快"，而是**打分逻辑应该用通用脚本表达，还是用引擎原生算子表达**。

`script_score` 给你的是无限灵活性：任何能用代码写出来的公式都能塞进去。代价是它对引擎不透明，没法优化，开销随命中量线性增长。`function_score` 牺牲了一部分灵活性——你得把排序意图拆解成衰减、字段因子这些预定义形状——但换来的是引擎级的执行效率。

绝大多数"距离 + 几个质量分加权"的排序需求，其实都能被 `function_score` 的内置 function 覆盖。当我发现自己在脚本里写的无非是"距离衰减 + 几个字段加权求和"时，那就是该把它翻译成原生算子的信号。

经验可以反过来用：**当排序逻辑能被几个标准 function 表达、而候选集又很大时，优先 `function_score`；只有当打分确实复杂到没有原生算子能表达、且候选集已被过滤得足够小时，才回退到 `script_score`。** 顺序别搞反——先压候选集，再考虑要不要上脚本。
