我现在大部分活是在 AI 编码工具里干的。一天下来，可能开了七八个会话：上午在排查一个查价的 bug，中午顺手补了个数据回填脚本，下午又在另一个项目里调前端。每个会话都是一段独立的对话记录，躺在本地。

到了晚上要写日报，问题就来了。手写太烦——我得自己回忆今天到底干了啥。可要是直接把会话记录导出来糊成一篇，那就是一坨没法看的流水账：每条会话各说各的，同一件事被拆在三个会话里，读的人根本理不清今天到底产出了什么。

折腾了几版之后，真正让这件事跑顺的，是一个看起来有点反直觉的决定：**把它拆成两步，中间隔一层结构化数据。**

## 为什么不能一步到位

最自然的想法当然是一步搞定：写个脚本，把当天所有会话喂给 AI，让它"读完这些，给我写份日报"。

我试过，效果不好。会话原始记录里全是噪音——工具调用的参数、一长串报错、我中途打断重来的废话、模型的自我纠正。直接整个塞进去，AI 要么被细节带跑、把某个无关紧要的小插曲写得很重，要么为了"覆盖全部"而记成流水账。更别提原始记录里夹着一堆敏感信息：服务器 IP、内部接口名、数据库地址、API key。

根本原因是，这一步其实在同时干两件性质不同的事：一件是**机械的提取**（从杂乱日志里把"我今天做了哪些事"捞出来），一件是**有判断的写作**（把这些事按逻辑合并、排序、表达成人话）。把它们混在一个 prompt 里，两件都做不好。

## 第一步：导出干净的 raw

所以第一步只干一件事：把当天每个会话压成一条结构化记录，存成 JSON。

这一步基本是确定性的，不需要 AI 发挥。每个会话提取成固定的几个字段——做了什么、涉及哪个项目、改了哪些文件、跑了哪些命令、打了什么标签。输出长这样：

```json
{
  "date": "2026-05-30",
  "session_count": 8,
  "sessions": [
    {
      "thread_id": "...",
      "cwd": "/path/to/project",
      "user_messages": ["帮我查一下查价这里的房型映射..."],
      "tags": ["数据库", "接口梳理"]
    }
  ]
}
```

raw 这一层的价值在于，它把"今天发生了什么"固化下来了，而且是机器友好的格式。后面无论整理成日报、挑博客选题，还是哪天想做点别的统计，都从这一份干净的 raw 出发，不用每次都回去啃原始日志。

## 第二步：按事项合并，而不是按会话罗列

第二步才轮到 AI 发挥，而且任务很明确：读 raw，按**工作事项**重新组织，写成日报。

"按事项"是这一步的灵魂。我上午和下午可能在三个不同会话里都碰了同一个查价 bug，机械罗列会把它拆成三条；但在日报里，它就该是一件事——"修复查价房型映射问题"，下面把过程和结果讲清楚。反过来，一个会话里如果我穿插干了两件不相干的事，也该拆开写。

会话的边界和工作的边界，根本不是一回事。这一步的全部意义，就是把记录的结构从"按会话"翻译成"按事项"。这种归并、取舍、判断主次的活，恰恰是 AI 擅长、而固定脚本做不了的。

## 一条我特意定死的规矩：不准自动写博客正文

整理日报的同时，我让它顺手再干一件事：从今天的工作里挑出**值得写成博客的选题**，但只输出选题卡片——标题、为什么值得写、建议角度、哪些信息要脱敏——而**绝不自动生成博客正文**。

这条规矩是我特意设的边界。日报是给"过去"做记录的，事实导向，可以放心自动化；博客是要对"读者"负责的，得有真实的思考和把关。如果让流水线自动把工作记录扩写成博客，产出的就是那种正确但空洞、一眼假的"AI 文"——我宁可它只给我一张选题卡，正文等我自己有空、有想法了再动笔。

（你正在看的这篇，就是从那样一张选题卡来的。）

把这条边界明确写进流程后，整个自动化的输出反而更清楚了：raw 负责"事实"，日报负责"把事实讲成人话"，选题卡负责"指出哪些事实值得展开"——三层各管各的，谁也别越界。

最近我把会话来源从单一工具扩到了两个，这套两阶段结构基本没动——因为它从一开始就没绑死在某个工具上。第一步无论从哪导，吐出来的都是同一种 raw；第二步只认 raw，不关心它从哪来。**先想清楚中间那层数据长什么样，上下游各自的职责自然就清楚了**——这大概是这次最省事的一个决定。
