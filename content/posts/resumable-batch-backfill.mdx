接到的活听上去很简单：业务酒店表里有一批数据，国家、省、市这几个字段是空的，需要从另一张第三方来源表里把它们补回来。几百万行。

如果这是一张测试库的小表，一条 `UPDATE ... JOIN ... SET` 就结束了。但它是线上库，而且体量不小。真正让我停下来的不是 SQL 怎么写，而是几个更现实的问题：这条语句跑起来会不会把库拖垮？跑到一半连接断了怎么办？万一映射关系有问题，会不会把本来好好的数据覆盖坏？

所以我没急着写 SQL，先给自己定了三条规矩。

## 只填空的，绝不覆盖

第一条最重要：**这个脚本只允许往空字段里写，已经有值的一律不碰。**

听起来是废话，但它直接决定了脚本的安全边界。一旦写错了映射，最坏的结果也只是"某些空字段没补上"，而不是"把一批正确的城市改成了错的"。前者重跑一次就好，后者可能要从备份里捞数据。

落到代码上就是更新条件里那一串看着啰嗦的判断：

```sql
UPDATE hotel h
JOIN supplier_addr s ON h.supplier_id = s.id
SET h.country = s.country,
    h.province = s.province,
    h.city = s.city
WHERE h.source = 'X'
  AND (h.country IS NULL OR h.country = '')
  AND s.country IS NOT NULL
LIMIT 2000;
```

`WHERE` 里那几个空值判断不是为了好看，是这个脚本的安全带。源表字段也得判空——你不想用一个空值去"覆盖"另一个空值，白白产生一次没意义的写入。

## 一次两千行，不是一次三百万行

第二条：分批。

把三百万行塞进一条语句，对数据库意味着一个长事务、一大片行锁、一份巨大的 binlog，以及一个在你盯着它的几分钟里别人都得排队的主库。这不是性能问题，是稳定性问题——你在拿整个库的可用性赌这条语句能顺利跑完。

所以每批只处理两千行，跑完一批、提交、喘口气、再来下一批。单批锁的范围小，事务短，主从延迟也压得住。代价是总时间变长，但批量数据修复这种活，慢从来不是问题，**把线上搞抖了才是问题。**

## 跑挂了，得能接着跑

第三条：可恢复。

几百万行分批跑，过程动辄几十分钟上小时。这么长的窗口里，网络抖一下、连接被中间件掐了、我自己手贱 Ctrl-C 了——什么都可能发生。如果一断就得从头来，那这脚本基本没法用。

我给它加了两样东西。一是**断点（checkpoint）**：每跑完一批，就把进度记到一个本地文件里，下次启动先读这个文件，从上次的位置接着往下，而不是重新扫一遍。二是**读连接重试**：读取映射数据时如果连接断了，退避几秒重连再试，而不是直接抛异常退出。

```python
last_id = load_checkpoint()           # 上次跑到哪了
while True:
    rows = fetch_batch(after=last_id, size=2000)   # 带重试
    if not rows:
        break
    apply_updates(rows)               # 只填空字段
    last_id = rows[-1].id
    save_checkpoint(last_id)           # 跑一批存一次
```

有了这两样，这脚本就从"一锤子买卖"变成了"随时可以掐断、随时可以接上"。我实际也是分两段跑完的，中间停过，再启动时它自己从断点接上了，前后一共写了五十八万多条。

## 最后一步：分清谁的锅

脚本跑完，复查阶段才是容易被忽略、但其实最该认真做的一步。

跑完之后，表里还是有一部分酒店的国家、省、市是空的。问题来了：这是我的脚本漏了，还是源数据本来就没有？

这两种情况的处理方式完全相反。如果是脚本漏了，我得回去查逻辑、补上;如果是源数据本身就缺、或者压根找不到有效映射，那这些就是补不上的，再跑多少遍都没用，得当成已知缺口记下来，而不是反复折腾。

所以我又写了一段只读的核对：把剩下的空值捞出来，逐个回去看它在源表里到底有没有对应、对应记录里那个字段是不是也是空的。查下来，剩余的缺失基本都落在"源数据本身不完整"和"没有有效映射"这两类——也就是说，能补的都补上了。

这一步给了我一个干净的收尾结论，而不是含糊的"差不多补完了"。批量数据任务最怕的就是这种含糊：你以为补完了，过两周有人发现还有一堆空的，又得重新排查一遍到底是哪儿的问题。把"补不上的原因"也一并查清楚、记下来，这事才算真的结了。

回头看，这次真正可复用的东西，不是那段 SQL，而是处理大批量修复的那套姿势：**只动该动的、小步写、能续跑、跑完还要能解释剩下的为什么没动。** 数据量越大、库越重要，这套姿势就越值钱。
